## 根因判定（高置信）

- 失败调用来自自研适配器 `quoteNetzipWine/src/dll.rs::DllRuntime::initialize()` 的第 1 条
  命令 `股票数据?请求=登录&模块=认证&账号=...&密码=...&自动升级=稳定版&版本=20221120&等待=10000&编号=0`，
  是 main() 启动后同步调用的旧式登录 Ask。
- 脱敏诊断标记（`[请求=登录&模块=认证&自动升级=稳定版&版本=20221120&等待=10000&编号=0]`）
  证明 Ask=0 的是这条命令，不是备用/初始化、也不是网际风内部某个随机调用。
- Ask=0 之后 24ms vendor 就把已登录的主站断开并切备用 → 因果而非巧合。
- 结论：**旧式同步 `模块=认证` 登录 Ask 与网际风(配置文件自动登录)的主站连接互相打架/超时，
  vendor 把 Ask 失败解释为“登录股票主站失败→断开主站→改用备用”。**
- 此前两轮（1705/1722 等）观察到的“主站登录成功→约3~6s后 Ask returned 0→断开→备用成功”
  是同一机制。callback 队列 8→65536→1024 均不能消除，与本根因一致。

## 被排除的假设

- 非 callback 背压：队列 65536 后仍 3s 掉线（1722 run）。
- 非服务端主动踢：5188 各连接在断开前服务端持续正常推送，FIN/RST 由本地 wine 主动发出
  （17:22 run pcap：所有 10 条连接在 ~38.0s 由本机同时 FIN+RST）。
- 非 Wine 环境差异导致拿不到服务器列表：L1 4 endpoint 正常获取、222.85.139.177 被选、10 条
  5188 建连并完整初始化。
- 非 2a10 订阅形状/初始化字节错误：断开发生在业务帧正常推送阶段之后。

## 修复方向

- `DllRuntime::initialize()` 不应再同步发送旧式 `模块=认证/编号=0` 登录 Ask（它会触发断开）。
- 让网际风（`用户/配置文件.ini` 已含账号密码与 `自动登录=1`，vendor_prelaunch 已启动）自行完成
  认证+主站登录；DLL 只保留 Start/连接与只读查询。
- 判别实验：注释/跳过 initialize 的三条 Ask（或仅保留安全命令），冷启动后观察主站是否持续
  >120s 不掉、5188 10 条连接保持、事件不再出现 Ask returned 0。
- 若完全跳过 initialize 后主站不再被登录（无行情授权），则改为：Ask 仅做 `模块=股票主站` 或
  `编号=-1 初始化` 且不触发旧式认证登录，或接受 vendor 授权流程所需的最小调用。

## 未决问题

- `Ask(模块=认证)` 超时返回 0 的确切内部原因（与网际风自身自动登录是否重复/冲突）尚待 vendor
  内部解释；但已无需解释即可修复：避免该旧式 Ask。
- 配置文件被 vendor 写回 `登录股票主站=0` 只是断开的结果，不是原因。
